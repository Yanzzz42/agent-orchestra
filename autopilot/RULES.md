# 自動駕駛共通規則

使用者在儀表板上逐一開關專案。排程每 3 小時喚醒 Claude 一次，`dispatch.mjs autopilot check` 會列出開啟中的專案。
Claude 在這些專案之間**輪流**，每個專案做一項改動再換下一個，一直做到額度用完或專案都被關掉。
每個專案另有自己的規則檔（`autopilot/<專案id>.md`），寫著專案資訊、額外禁止事項、待辦和紀錄。專案規則和這份衝突時，以比較嚴格的為準。

D=`{{ORCHESTRA_HOME}}/orchestra/dispatch.mjs`（`{{ORCHESTRA_HOME}}` 是這個工具的安裝資料夾，實際路徑寫在 `~/.claude/skills/team/SKILL.md`）

## 發佈方式（由使用者在儀表板設定，看 `check` 輸出的 `publish`）

- `auto`（測試通過自動發佈）：測試全過才 commit，再推到專案規則檔寫的發佈分支／方式。專案規則檔沒寫清楚怎麼發佈 → 當成 `commit` 處理，並在待辦記下「需要使用者補上發佈方式」。
- `commit`（只 commit 不發佈）：測試全過就在目前分支 commit，不 push、不部署。

## 第一次處理某個專案

規則檔的「專案資訊」還是空的時候，先用唯讀方式（可派 `flash`／`opus`）查清楚並填上：
語言與框架、怎麼安裝相依套件、**測試指令**、git 遠端與預設分支、怎麼部署（有沒有 Render／Vercel／GitHub Pages 等自動部署）、正式站網址。
沒有測試的專案：只做能用建置、lint 或實際執行驗證的改動，並優先把「補上基本測試」列為第一項待辦。
接著做一次健檢，把具體問題寫進待辦，這一輪該專案就算完成。

## 每一項改動的流程

1. 進入專案資料夾，`git status`：工作目錄不乾淨（使用者可能正在改）→ 這一輪跳過這個專案，不要動任何檔案。
2. 有遠端就 `git pull --rebase`；有衝突 → 跳過這個專案並記錄。
3. 從專案規則檔「待辦」挑最上面一項沒做的；待辦空了就派 `flash` 或 `opus` 做一次健檢（唯讀），把找到的具體問題寫進待辦再挑。
4. 寫好給子代理的 prompt（目標、檔案、限制、完成的定義），依 `node $D usage` 派給有額度的 agent，`--cwd` 指向專案資料夾。
   大量閱讀、review 優先派 `flash`／`opus`，寫程式派 `codex`／`opus`（`--write`）。
5. 自己驗收：看 `git diff`、跑專案的全部測試。失敗就請同一個 agent 修，最多兩次；還是不過就 `git checkout -- . && git clean -fd`（只清掉這次新增的檔案）放棄這項，在待辦標記 ❌ 和原因。
6. 通過後：有版號檔就升 patch 版號、有 CHANGELOG 就加一條；commit 訊息結尾加 `（autopilot）`。
7. 發佈方式是 `auto`：照專案規則檔的方式發佈（通常是 `git pull --rebase` 後 `git push`），被拒絕就再 pull 一次重試。
   有正式站網址就在部署完成後確認首頁或健康檢查回 200；失敗 → `git revert` 這個 commit 再發佈一次，待辦標記 ❌。
8. 在專案規則檔「紀錄」加一行，`node $D autopilot check <專案id>`：不是 ENABLED 就不再碰這個專案。然後換下一個專案。

## 什麼時候收尾

- 用量守護觸發：每做完一項都用 `get_usage` 讀 Claude 每週用量並執行 `node $D autopilot guard <每週%> <每週重置時間> <5 小時%>`，結束碼 12 就收尾（使用者在儀表板設定門檻；觸發後暫停到每週額度重置，會自己恢復）。
- `node $D autopilot check` 不是 ENABLED（所有專案都被關掉了）。
- 所有 agent 都用量不足，Claude 自己也做不動了 → 下一次喚醒再繼續。
- 所有開啟的專案都找不到值得做的事。

收尾時執行 `node $D autopilot end "摘要"`：每個專案完成幾項、發佈到哪個版本、放棄了什麼、為什麼停下來。

## 所有專案都不可以做的事

- 不碰 `.env`、金鑰、憑證，不改部署平台或 GitHub 的設定、環境變數。
- 不做會刪除或破壞使用者資料的變更（刪表、刪欄位、清資料、刪使用者檔案）。
- 不放寬登入、權限、CSRF 等安全檢查；不刪測試、不為了讓測試通過而改弱斷言。
- 不 force push、不改寫已推上去的歷史、不建立新的 repo 或外部服務、不花錢。
- 不動工作目錄不乾淨的專案，也不切換使用者正在用的分支。
- 不做大改版（換框架、重寫整個頁面）；一項改動應該一個 commit 就能說清楚。
- 沒有實際價值的改動（只改空白、無意義的重構）不要做。
- 遇到不確定是否安全的改動就跳過，寫進待辦讓使用者決定。
